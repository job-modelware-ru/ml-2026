## 1. Цель работы за период

Основной целью недели было привести исследовательский инструмент к формату, удобному для длительной ручной разметки, и проверить, насколько текущие признаки и модели согласуются с ручной проверкой новых Hansen-кандидатов.

Работа велась по трём направлениям:

- рефакторинг интерфейса ResearchTool;
- исследование структуры текущей валидной выборки в пространстве RemoteCLIP-признаков;
- ручная проверка новых событий и сравнение результатов двух моделей с человеческой разметкой.

## 2. Рефакторинг интерфейса ResearchTool

### 2.1. Переработка основного рабочего пространства

Интерфейс был упрощён вокруг основного сценария работы: выбрать территорию, посмотреть событие Hansen, сравнить спутниковые снимки и сохранить решение.

В левой панели оставлены только основные фильтры и список территорий. Из постоянно видимой части убраны редко используемые поля поиска по файлу, региону и числу ближайших точек. Значение `Nearest N` сохранено как внутреннее значение по умолчанию — 25 точек. Карточки samples сделаны компактнее, чтобы идентификатор, тип события и статус помещались без горизонтального переполнения.

С карты убрана перегруженная нижняя информационная область. Основные действия перенесены в правый верхний угол карты:

- открытие PRE/POST Compare;
- просмотр информации о выбранной территории;
- открытие панели Events & Sentinel;
- открытие и скрытие панели слоёв.

Кнопки приведены к единому размеру и состояниям наведения. Панель слоёв, информационная панель и инспектор снимков открываются поверх рабочего пространства и не требуют прокрутки всей страницы. Нижний служебный drawer оставлен сворачиваемым и используется только для операций уровня базы данных и Data Operations.

### 2.2. Панель Events & Sentinel

Список событий и снимков перенесён в отдельную правую панель. За счёт этого вся высота окна используется для просмотра данных, а список изображений больше не конкурирует за место с картой.

Панель содержит:

- список Hansen events по годам;
- площадь потери леса и признак доминантного события;
- статусы `DRAFT`, `VALID` и `REJECTED`;
- прогресс разметки вида `reviewed / total`;
- Sentinel-2-снимки, относящиеся к выбранному событию;
- группировку снимков по `PRE`, `EVENT` и `POST`;
- поиск и загрузку дополнительных сцен;
- существующую разметку качества снимков и причины исключения.

Редактор исключения снимка сохранён в контексте конкретного изображения. Причины выбираются как множественный список; для причины `OTHER` доступно дополнительное текстовое поле. Изменения можно отдельно сохранить или отменить, не меняя состояние остальных снимков.

### 2.3. Последовательная разметка нескольких событий

Ранее после подтверждения доминантного события территория могла исчезать из текущей рабочей выборки, хотя у неё оставались непроверенные годы. Это делало разметку multi-event samples неудобной.

Новый сценарий работает следующим образом:

1. после сохранения решения для события ищется следующее событие со статусом `DRAFT` в той же точке;
2. панель автоматически переключается на найденный год;
3. для полностью размеченной территории показывается итоговый статус;
4. пользователь явно выбирает: остаться на территории или перейти к следующей точке.

Таким образом, единицей ручной проверки теперь является не только sample, но и отдельное событие конкретного года.

## 3. Анализ структуры валидной выборки

### 3.1. Состав анализируемых данных

Анализ проводился только по событиям, уже относящимся к когорте `MANUAL_VALID`. Для каждого события использовались POST-снимки Sentinel-2 и сохранённые RemoteCLIP embeddings. В этой части эксперимента классы `Logging` / `Wildfire` берутся из исходной разметки набора, а ручной статус подтверждает пригодность события и снимков; это не полностью независимая повторная разметка класса.

| Показатель | Значение |
|---|---:|
| Территории | 139 |
| События | 149 |
| POST-снимки | 452 |
| Снимков на событие, медиана | 3 |
| Снимков на событие, диапазон | 1–9 |
| `Logging` | 79 |
| `Wildfire` | 70 |
| Размер исходного embedding | 512 |

Перед кластеризацией embeddings были L2-нормализованы. Для уменьшения размерности применён PCA:

| Сохранённая дисперсия | Компоненты |
|---|---:|
| 90% | 49 |
| 95% | 73 |

### 3.2. Методы анализа

Для проверки наличия естественной структуры в данных выполнены:

- KMeans для `k = 2…10`;
- оценка Silhouette, Davies–Bouldin и Calinski–Harabasz;
- проверка устойчивости кластеров на повторных подвыборках через Adjusted Rand Index;
- Gaussian Mixture Model с выбором числа компонент по BIC;
- HDBSCAN с перебором параметров и отдельным учётом noise points;
- сравнение кластеров с известными классами только после обучения кластеризации.

Классы `Logging` и `Wildfire` не использовались для построения кластеров и добавлялись после расчёта только для интерпретации результата.

### 3.3. Результаты кластеризации

Лучшее значение Silhouette получено для `k = 3`, но оно составило только `0,092`. Это указывает на слабое разделение классов и наличие плавных переходов в пространстве признаков. Для `k = 3` средняя устойчивость кластеризации на 20 повторных подвыборках составила `ARI = 0,844`, а GMM также выбрала три компоненты по BIC.

| Кластер KMeans, `k = 3` | Всего событий | `Logging` | `Wildfire` | Интерпретация |
|---|---:|---:|---:|---|
| 0 | 45 | 45 | 0 | выраженный Logging-mode |
| 1 | 68 | 8 | 60 | преимущественно Wildfire-mode |
| 2 | 36 | 26 | 10 | смешанный режим |

Метрики не дали полностью единогласного выбора числа кластеров: Calinski–Harabasz предпочёл `k = 2`, Davies–Bouldin — `k = 9`, а Silhouette, stability и GMM — `k = 3`. Поэтому три кластера рассматриваются как удобная интерпретируемая модель структуры.

Для выбранной конфигурации HDBSCAN было найдено три компактных кластера с покрытием `67,1%`; `32,9%` событий были отнесены к noise. Это дополнительно показывает, что часть выборки образует устойчивые режимы, однако значительная доля событий не имеет плотного локального окружения.

### 3.4. Анализ переносимости на Hansen-кандидаты

Дополнительная диагностика сравнила ручную референсную когорту с новыми Hansen-кандидатами. Для анализа, требующего одновременно PRE и POST, использовались 135 ручных событий из 131 территории и 243 автоматически найденных события из 99 территорий.

Классификация по ближайшему классу в latent-пространстве дала на ручной когорте:

| Метрика | Значение |
|---|---:|
| Accuracy | 0,896 |
| Balanced accuracy | 0,895 |
| Recall `Logging` | 0,905 |
| Recall `Wildfire` | 0,885 |
| Согласие с RemoteCLIP LogReg | 90,4% |

При использовании нижних 5% ручного распределения `knownness_k5` как диагностического порога ниже него оказались 18 из 243 Hansen-событий, или `7,4%`. Следовательно, большая часть новых кандидатов находится рядом с уже известными режимами, но отдельная группа требует осторожной ручной проверки.

Сравнение двух моделей на 243 Hansen-событиях до ручной проверки показало:

| Сочетание предсказаний | События |
|---|---:|
| обе модели — `Logging` | 6 |
| обе модели — `Wildfire` | 184 |
| RemoteCLIP — `Logging`, XGBoost — `Wildfire` | 39 |
| RemoteCLIP — `Wildfire`, XGBoost — `Logging` | 14 |

Эти расхождения были использованы как один из ориентиров при формировании очереди ручной проверки.

## 4. Ручная проверка новых событий

### 4.1. Сформированная ручная когорта

За период была выполнена event-level разметка новых Hansen-кандидатов:

| Показатель | Значение |
|---|---:|
| Проверенные территории | 49 |
| Проверенные события | 102 |
| Принятые события (`VALID`) | 54 |
| Отклонённые события (`REJECTED`) | 48 |
| `Logging` среди принятых | 7 |
| `Wildfire` среди принятых | 47 |

Отклонённые события не считались ошибками моделей. Они анализировались отдельно, поскольку причиной отклонения могли быть отсутствие валидных PRE-снимков, слишком маленькое изменение, несовпадение года Hansen с фактически видимым событием или невозможность уверенно определить тип изменения.

Эталонный класс для принятого события брался только из текущего `EventReview.human_label_id`. Исторические HUMAN-labels, не связанные с актуальным review, в расчёт не попадали.

### 4.2. Сравнение RemoteCLIP и XGBoost

Обе модели имели сохранённые предсказания для всех 54 принятых событий.

| Модель | Accuracy | Balanced accuracy | Macro F1 |
|---|---:|---:|---:|
| RemoteCLIP LogReg | **0,944** | **0,786** | **0,848** |
| XGBoost | 0,870 | 0,500 | 0,465 |

Для оценки неопределённости дополнительно рассчитан grouped bootstrap по территориям, при котором все годы одного `sample_id` переносятся в одну bootstrap-группу:

| Модель | Accuracy, 95% CI | Balanced accuracy, 95% CI |
|---|---:|---:|
| RemoteCLIP LogReg | 0,850–1,000 | 0,500–1,000 |
| XGBoost | 0,754–0,980 | 0,500–0,500 |

Поклассовые результаты:

| Модель | Класс | Precision | Recall | F1 | События |
|---|---|---:|---:|---:|---:|
| RemoteCLIP LogReg | `Logging` | 1,000 | 0,571 | 0,727 | 7 |
| RemoteCLIP LogReg | `Wildfire` | 0,940 | 1,000 | 0,969 | 47 |
| XGBoost | `Logging` | 0,000 | 0,000 | 0,000 | 7 |
| XGBoost | `Wildfire` | 0,870 | 1,000 | 0,931 | 47 |

Совместный результат моделей:

| Результат | События | Доля |
|---|---:|---:|
| обе модели правы | 47 | 87,0% |
| права только RemoteCLIP | 4 | 7,4% |
| обе модели ошиблись | 3 | 5,6% |
| прав только XGBoost | 0 | 0% |

### 4.3. Интерпретация ручной проверки

Обычная accuracy XGBoost выглядит сравнительно высокой из-за сильного дисбаланса новой ручной когорты: 47 из 54 событий относятся к `Wildfire`. На этой подвыборке XGBoost не распознал ни одного из семи событий `Logging` и фактически предсказал `Wildfire` для всех принятых событий. Поэтому более показательными здесь являются balanced accuracy и поклассовый recall.

RemoteCLIP корректно определила все 47 пожаров и четыре из семи вырубок. Ещё три вырубки обе модели приняли за пожар. Это делает такие события приоритетными для отдельного визуального разбора и возможного расширения обучающей выборки.

Полученные показатели пока нельзя считать финальной оценкой моделей: ручная когорта мала, а класс `Logging` представлен только семью событиями. Результат показывает текущее поведение моделей на новых Hansen-кандидатах и должен пересчитываться после завершения оставшейся разметки.

## 6. Основные ограничения

- ручная когорта пока содержит только семь принятых событий `Logging`, поэтому доверительный интервал balanced accuracy RemoteCLIP остаётся широким;
- event-level строки одной территории не являются полностью независимыми, поэтому для доверительных интервалов использовалась группировка по `sample_id`;
- слабый Silhouette и большая доля HDBSCAN noise показывают, что классы не образуют полностью разделённых кластеров в POST-пространстве;
- кластеризация описывает структуру выборки, но не заменяет supervised-оценку на независимом test set;
- классы в исследовании структуры MANUAL_VALID-выборки сохраняют происхождение из исходной разметки, поэтому этот анализ нельзя интерпретировать как независимую оценку ground truth;
- причины `REJECTED` пока вводятся свободным текстом и содержат близкие по смыслу формулировки, которые перед общей статистикой желательно нормализовать.
