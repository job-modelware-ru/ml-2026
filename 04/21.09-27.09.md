# Отчёт за 21.09–27.09

**Проект:** «Интеллектуальная система классификации нарушений лесного покрова по спутниковым данным»

**Команда:** 4

## Ключевые результаты недели

- база расширена до 1 178 forest samples;
- накоплено 2 160 Sentinel-2 GeoTIFF и 12 960 derived previews;
- реализована multi-label разметка причин исключения Sentinel-снимков;
- подготовлены import/export cache bundle и repair-скрипты для переноса и восстановления локального кэша;
- проведён первый расширенный эксперимент с RemoteCLIP;
- для `POST` получено `balanced accuracy = 0.955 ± 0.045`;
- высокая разделимость по `PRE` (`balanced accuracy = 0.846 ± 0.071`) показала необходимость отдельной проверки пространственного и контекстного смещения.

## 1. Цель работы за период

На этой неделе работа была сосредоточена на расширении рабочего набора спутниковых данных, улучшении качества разметки и подготовке инфраструктуры для совместной работы нескольких участников с одной базой Forest samples.

Основная цель периода — перейти от индивидуального локального инструмента к более устойчивому исследовательскому контуру, в котором можно:

- массово скачивать и проверять Sentinel-2 снимки;
- автоматически выявлять снимки с признаками низкого качества и формировать кандидатов на исключение из выборки;
- хранить несколько причин исключения снимка из выборки;
- сравнивать и переносить локальные кэши между машинами;
- готовить синхронизацию разметки между несколькими SQLite-базами;
- удобнее работать со слоями Hansen и Sentinel Scene Classification Layer;
- начать проверку пригодности RemoteCLIP-эмбеддингов для классификации по спутниковым снимкам.

Параллельно с развитием инструмента разметки были проведены первые эксперименты с RemoteCLIP на текущем наборе изображений. В этом отчёте они фиксируются как отдельное исследовательское направление: пока проверяется не финальная модель, а гипотеза, что спутниковые изображения PRE/POST уже содержат различимый сигнал для классификации.

## 2. Используемые источники данных

Набор источников остался тем же, что и в предыдущем отчётном периоде.

### 2.1. Global Drivers of Forest Loss

В качестве исходной разметки используются samples из набора **Global drivers of forest loss at 1 km resolution**. Он задаёт исходный класс нарушения лесного покрова, например `Logging`, `Wildfire`, `Permanent agriculture`, `Hard commodities` и другие.

Документация и загрузка:

- Zenodo: [Global drivers of forest loss at 1 km resolution](https://zenodo.org/records/19485190)
- Google Earth Engine Data Catalog: [WRI/Google DeepMind Global Drivers of Forest Loss 2001-2025 v1.3](https://developers.google.com/earth-engine/datasets/catalog/projects_landandcarbon_assets_wri_gdm_drivers_forest_loss_1km_v1_3_2001_2025)
- WRI Data Explorer: [Global drivers of forest loss at 1 km resolution](https://datasets.wri.org/datasets/dominant-drivers-of-tree-cover-loss-at-1km)

### 2.2. Hansen Global Forest Change

Для оценки года события используется **Hansen Global Forest Change 2000-2025 v1.13**. Основной слой — `lossyear`, где значение пикселя кодирует год потери леса как смещение относительно 2000 года.

Документация и загрузка:

- [Global Forest Change 2000-2025 Data Download](https://storage.googleapis.com/earthenginepartners-hansen/GFC-2025-v1.13/download.html)
- [GLAD Global Forest Change viewer](https://glad.earthengine.app/view/global-forest-change)
- Google Earth Engine asset: `UMD/hansen/global_forest_change_2025_v1_13`

Hansen используется не как финальная ground truth-разметка, а как вспомогательный источник для:

- определения dominant event year;
- фильтрации слишком старых событий;
- поиска samples с несколькими событиями потери леса;
- построения масок `dominant_year`, `all_loss`, `treecover2000`;
- подготовки численных признаков для последующего ML.

### 2.3. Sentinel-2 L2A / Copernicus Data Space

Для визуальной проверки событий и формирования PRE/POST контекста используется **Sentinel-2 L2A** через Copernicus Data Space / Sentinel Hub API.

Документация:

- Copernicus Data Space APIs: [APIs overview](https://documentation.dataspace.copernicus.eu/APIs.html)
- STAC catalogue: [STAC product catalogue](https://documentation.dataspace.copernicus.eu/APIs/STAC.html)
- Sentinel-2 L2A: [Sentinel-2 L2A documentation](https://documentation.dataspace.copernicus.eu/APIs/SentinelHub/Data/S2L2A.html)
- Sentinel Hub S2L2A data notes: [Sentinel-2 L2A](https://docs.sentinel-hub.com/api/latest/data/sentinel-2-l2a/)

Ограничение по датам остаётся важным: события до 2016 года выделяются в статус `Too old`, потому что для них нельзя корректно собрать сопоставимый Sentinel-2 L2A PRE/EVENT/POST-контекст.

### 2.4. RemoteCLIP

Для первых экспериментов с классификацией по изображениям используется RemoteCLIP в варианте `ViT-B-32`. Модель загружается через `open_clip`, а веса берутся из локального checkpoint:

```text
checkpoints/models--chendelong--RemoteCLIP/snapshots/.../RemoteCLIP-ViT-B-32.pt
```

В текущем контуре RemoteCLIP используется как feature extractor:

- на вход подаются RGB preview-изображения Sentinel;
- для каждого изображения считается нормированный image embedding;
- embeddings агрегируются по `sample_id` и периоду `PRE`/`POST`;
- далее проверяется, насколько embeddings разделяют классы текущего датасета.

## 3. Что было сделано

### 3.1. Расширение Sentinel-2 выборки

За период вырос объём локально сохранённых Sentinel-2 данных. В базе увеличилось количество найденных и скачанных снимков, а для каждого GeoTIFF формируются derived previews:

- RGB;
- False Color;
- NDVI;
- NBR;
- NDMI;
- SCL.

Снимки сохраняются как локальный кэш, а в SQLite хранится метаинформация: `download_id`, `sample_id`, `scene_id`, период `PRE`/`EVENT`/`POST`, путь к GeoTIFF, метрики качества и ссылки на preview-слои.

### 3.2. Скрипт массового скачивания Sentinel для кандидатов

Добавлен вспомогательный скрипт:

```text
Scripts/ResearchScripts/download_unvalidated_sentinel.py
```
Он нужен для массового пополнения выборки снимками для ещё не размеченных кандидатов.

Текущие правила отбора samples:

- берутся samples без записи в `forest_manual_validations`;
- рассматриваются классы `Logging` и `Wildfire`;
- проверяются как `driver_primary`, так и `driver_secondary`;
- исключаются точки со статусом Hansen `TOO_OLD`;
- `event_year` берётся из последнего Hansen-анализа, если он есть, иначе из исходного `source_event_year`;
- за один запуск берётся не больше `LIMIT_SAMPLES = 100`;
- можно ограничить запуск конкретными `sample_id` prefix-ами.

Текущие правила поиска и скачивания Sentinel:

| Параметр | Значение |
|---|---:|
| Периоды | `PRE`, `POST` |
| Season preset | `full_snow_free` |
| STAC scene-level cloud filter | `max_cloud = 30%` |
| Кандидатов из поиска на период | top `40` |
| Максимум принятых снимков на период | `10` |
| Минимальный интервал между принятыми снимками | `7` дней |
| Локальный cloud threshold по AOI | `10%` |

Важно, что STAC cloud filter используется только как грубый фильтр на уровне сцены. После скачивания снимок оценивается локально по конкретному AOI. Если локальная облачность выше `10%`, снимок может быть сохранён в кэш, но автоматически получает exclude-разметку с причиной `CLOUDS`.

Скрипт также учитывает уже скачанные снимки: существующие не excluded-снимки могут засчитываться в лимит, а слишком близкие по дате кандидаты пропускаются.

### 3.3. Контур автоматической проверки качества Sentinel-снимков

Добавлен и доработан модуль автоматической оценки качества скачанных Sentinel-2 снимков. Он используется как предварительный QC-контур: автоматически выявляет изображения с признаками низкого качества и формирует кандидатов на исключение или дополнительную ручную проверку.

Основные признаки качества:

- локальная облачность по SCL;
- cloud shadow по SCL;
- отсутствие данных / чёрные области;
- слишком тёмное и низкоконтрастное изображение;
- локальные brightness-метрики по clear pixels.

Для SCL сейчас используются следующие классы:

| Тип | SCL classes |
|---|---|
| Clouds | `8`, `9`, `10` |
| Cloud shadow | `3` |

Порог локальной облачности для автоматической оценки сделан более строгим, чем порог первичного поиска сцен. Это разделение важно: при поиске по каталогу допустим более мягкий фильтр, а после скачивания AOI оценивается уже конкретный локальный участок.

Текущие правила автоматической отбраковки снимков:

| Причина | Правило |
|---|---|
| `CLOUDS` | `cloud_fraction > 0.10`, где clouds считаются по SCL-классам `8`, `9`, `10` |
| `CLOUD_SHADOW` | `shadow_fraction > 0.35`, где shadow считается по SCL-классу `3` |
| `NO_DATA_OR_BLACK_PIXELS` | `nodata_fraction > 0.10` или отсутствуют valid pixels |
| `DARK_AND_LOW_CONTRAST` | снимок одновременно слишком тёмный и низкоконтрастный по clear pixels |

`valid pixels` считаются по `dataMask`, дополнительно отбрасываются полностью пустые пиксели, где сумма Sentinel bands равна нулю. Метрики яркости считаются по clear pixels, то есть без облаков и cloud shadow.

Для тёмных снимков зафиксировано рабочее правило:

```text
brightness_p95 < 350
AND
(
    brightness_p95 - brightness_p05 < 100
    OR
    (brightness_p95 - brightness_p05) / brightness_p50 < 0.30
)
```

Такие снимки получают причину `DARK_AND_LOW_CONTRAST`.

Дополнительно сохраняются диагностические метрики:

- `cloud_fraction`;
- `shadow_fraction`;
- `nodata_fraction`;
- `dark_fraction`;
- `brightness_p05`;
- `brightness_p50`;
- `brightness_p95`;
- `brightness_p95_minus_p05`;
- `brightness_relative_contrast`.

`dark_fraction` пока используется как диагностический показатель, а не как самостоятельное правило исключения: production-правило для тёмных снимков основано на `p95` и контрасте.

### 3.4. Несколько причин исключения Sentinel-снимка

Ранее для Sentinel-снимка можно было сохранить только одну причину исключения. На практике у одного изображения может быть несколько проблем одновременно: например, облака и тени, облака и отсутствие данных, низкий контраст и артефакты.

Для этого добавлена отдельная таблица:

```text
forest_sentinel_scene_review_reasons
```

Теперь состояние снимка хранится так:

- `forest_sentinel_scene_reviews` — общий review по `download_id`;
- `forest_sentinel_scene_review_reasons` — набор причин для этого review.

Старые данные не теряются: старая причина из `forest_sentinel_scene_reviews.reason_code` мигрируется в новую таблицу причин.

В UI вместо одиночного выбора причины появился набор checkbox-ов. Снимок можно исключить сразу по нескольким причинам.

### 3.5. Автоматическая разметка невалидных снимков

Скрипт автоматической проверки качества адаптирован под новую модель с несколькими причинами. Он:

- проходит по скачанным Sentinel downloads;
- пересчитывает локальные метрики качества;
- сравнивает автоматическое решение с текущей ручной разметкой;
- печатает статистику по каждому типу исключения;
- показывает расхождения вида "ручная разметка считает OK, автомат считает exclude";
- в apply-режиме может проставить `is_excluded` и набор причин в базу.

Это формирует основу для полуавтоматической очистки выборки: человек не обязан просматривать все плохие снимки с нуля, а может проверять уже предложенную автоматическую разметку.

### 3.6. Samples с несколькими событиями

Добавлен флаг `has_multiple_events` для samples. Он нужен для случаев, когда в выбранной области Hansen показывает несколько разных годов потери леса после 2016 года.

Логика:

- dominant year остаётся основным годом события;
- если в области встречается несколько значимых годов потери леса, sample можно отметить как `Multiple loss events`;
- это помогает отделять простые случаи для ML от неоднозначных участков, где визуальный PRE/POST анализ может быть сложнее.

### 3.7. PRE/POST compare-view

Доработан отдельный режим сравнения Sentinel-снимков `PRE` и `POST`.

Добавлено:

- два синхронизированных raster-viewer окна;
- выбор PRE-снимка;
- выбор POST-снимка;
- выбор слоя Sentinel: RGB, False Color, NDVI, NBR, NDMI, SCL;
- правый сворачиваемый Layers panel;
- наложение Hansen mask поверх обоих снимков;
- настройка opacity Hansen overlay;
- режим pixelated для raster masks.

Этот режим нужен для ручной проверки того, действительно ли видимое изменение на Sentinel соответствует предполагаемому событию потери леса.

### 3.10. Подготовка к многопользовательской разметке

Начата подготовка инфраструктуры для работы нескольких участников с одной выборкой.

Сформулирована отдельная задача на UI-синхронизацию баз:

Идея будущего инструмента:

```text
текущая база state.sqlite
+
внешняя база другого участника
→
compare
→
merge plan
→
backup
→
apply selected changes
```

Принципиальное решение: не заменять `state.sqlite` целиком, а строить diff и применять только выбранные изменения.

Для MVP предполагается сравнивать:

- manual validations;
- sample statuses;
- editable sample metadata;
- Sentinel scene reviews;
- Sentinel review reasons.

Файловый кэш Sentinel/Hansen не должен merge-иться как часть DB sync. Он синхронизируется отдельными cache-bundle/repair-скриптами.

### 3.11. Первые эксперименты с RemoteCLIP

Начаты эксперименты с классификацией по изображениям с использованием RemoteCLIP embeddings.

Файлы текущего экспериментального контура:

```text
Scripts/ResearchScripts/ml_tests/
Scripts/ResearchScripts/linear_probe_test.py
Scripts/ResearchScripts/open_clip_test.py
```

Текущая схема эксперимента:

1. Из папки `Scripts/ResearchScripts/Data/Images` читается `metadata/images_metadata.json`.
2. Изображения группируются по `sample_id` и периоду `PRE`/`POST`.
3. Для каждого изображения считается RemoteCLIP image embedding.
4. Embeddings внутри одного `sample_id + period` агрегируются усреднением.
5. Получаются признаки:
   - `PRE`;
   - `POST`;
   - `DELTA = POST - PRE`;
   - конкатенации `PRE + POST`, `POST + DELTA`, `PRE + POST + DELTA`.
6. Для первичной проверки используется linear probe: `StandardScaler + LogisticRegression`.
7. Валидация выполняется через `RepeatedStratifiedKFold`: 5 folds, 20 repeats.

Цель этого этапа — проверить, есть ли в изображениях разделимый сигнал для классификации, а не получить финальную production-модель.

Причина `TOO_DARK_OR_LOW_CONTRAST` относится к более ранней версии правила оценки яркости. Текущее production-правило использует более строгий критерий `DARK_AND_LOW_CONTRAST`, который требует одновременно низкой яркости и низкого контраста.

Статистика показывает, что основной источник автоматических исключений сейчас — облачность. При этом новая схема с несколькими причинами позволяет не терять дополнительные дефекты снимка: например, один и тот же снимок может быть одновременно cloudy и иметь shadow/no-data признаки.

Для `driver_primary in ('Logging', 'Wildfire')` сейчас выделен отдельный пул кандидатов для дальнейшего Sentinel/ML анализа:

| Показатель | Количество |
|---|---:|
| Samples `Logging`/`Wildfire` | 754 |
| Уже имеют ручную валидацию | 655 |
| Пока без ручной валидации | 99 |

Эта группа используется как один из ориентиров для массового скачивания новых PRE/POST снимков и последующей ручной проверки.

### 4.6. RemoteCLIP: предварительные результаты

Проведены первые эксперименты с RemoteCLIP embeddings на текущем наборе изображений. Это тест именно классификации по снимкам, а не по Hansen-табличным признакам.

#### PCA и similarity-анализ

Для агрегированных embeddings была построена PCA-проекция. Первые две компоненты объясняют ограниченную, но заметную часть дисперсии:

| Представление | Explained variance PC1 | Explained variance PC2 | Сумма |
|---|---:|---:|---:|
| PRE | 0.134 | 0.107 | 0.241 |
| POST | 0.151 | 0.120 | 0.271 |
| DELTA | 0.154 | 0.094 | 0.248 |

Также проверялось, выше ли cosine similarity внутри одного класса, чем между разными классами.

| Представление | Same class cosine | Different class cosine | Gap | p-value |
|---|---:|---:|---:|---:|
| PRE | 0.819 +/- 0.059 | 0.806 +/- 0.061 | 0.012 | 0.00010 |
| POST | 0.831 +/- 0.061 | 0.806 +/- 0.056 | 0.025 | 0.00010 |
| DELTA | 0.042 +/- 0.184 | 0.020 +/- 0.160 | 0.023 | 0.00230 |

Дополнительно сравнивался прирост разделимости от PRE к POST:

```text
POST - PRE observed gap = 0.01299
p-value = 0.00010
```

Интерпретация: POST-представления дают более выраженное разделение классов, чем PRE. При этом сама PRE-выборка также содержит статистически значимый class-related signal. Это означает, что различия между классами могут быть связаны не только с последствиями самого события, но и с ландшафтным контекстом, историей предыдущих нарушений и пространственным распределением samples.

Одновременно тест `POST - PRE` показывает статистически значимое усиление разделимости после события (`observed gap = 0.01299`, `p < 0.0001`). Поэтому в POST присутствует дополнительный сигнал, который не объясняется только исходным PRE-контекстом.

#### Linear probe

Поверх RemoteCLIP embeddings обучался простой linear probe:

```text
StandardScaler + LogisticRegression(class_weight="balanced")
```

Валидация:

```text
RepeatedStratifiedKFold, 5 folds x 20 repeats
```

Результаты:

| Признаки | Accuracy | Balanced accuracy | F1 | ROC-AUC |
|---|---:|---:|---:|---:|
| PRE | 0.850 +/- 0.068 | 0.846 +/- 0.071 | 0.843 +/- 0.072 | 0.938 +/- 0.048 |
| POST | 0.957 +/- 0.042 | 0.955 +/- 0.045 | 0.955 +/- 0.044 | 0.994 +/- 0.012 |
| DELTA | 0.808 +/- 0.082 | 0.794 +/- 0.087 | 0.794 +/- 0.090 | 0.888 +/- 0.064 |
| PRE + POST | 0.947 +/- 0.043 | 0.944 +/- 0.048 | 0.944 +/- 0.046 | 0.995 +/- 0.010 |
| POST + DELTA | 0.947 +/- 0.049 | 0.944 +/- 0.052 | 0.944 +/- 0.051 | 0.991 +/- 0.015 |
| PRE + POST + DELTA | 0.951 +/- 0.044 | 0.950 +/- 0.046 | 0.948 +/- 0.046 | 0.993 +/- 0.013 |

Предварительный вывод:

- RemoteCLIP embeddings уже дают сильный сигнал для классификации по изображениям;
- лучшим одиночным представлением оказался `POST`;
- добавление PRE/DELTA даёт сравнимый результат, но пока не превосходит POST радикально;
- результаты нужно дополнительно проверить на расширенной выборке и с контролем возможных источников смещения.

### 4.7. XGBoost baseline по табличным признакам Wildfire/Logging

Параллельно с экспериментами RemoteCLIP проведён опыт с градиентным бустингом над решающими деревьями (XGBoost) на табличных признаках. В качестве признаков использованы как результаты Hansen-анализа, так и спектральные статистики, извлечённые из GeoTIFF Sentinel-2.

Это отдельная постановка задачи, не связанная с RemoteCLIP: RemoteCLIP работает с изображениями (RGB-превью), XGBoost — с числовыми признаками, извлечёнными из GeoTIFF и Hansen. Метрики двух постановок нельзя сравнивать напрямую.

#### 4.7.1. Переход от исходной выборки к рабочей

В отчёте за 14.09–20.09 базовый набор составлял 1 178 samples по всем классам и статусам. Для текущего эксперимента выборка последовательно сужена:

| Шаг фильтрации | Осталось samples |
|---|---:|
| Исходный набор `forest_samples` | 1 178 |
| Только samples со статусом «Valid» в manual validation | 118 |
| После отбора классов «Wildfire» и «Logging» | 116 (74 «Logging» / 42 «Wildfire») |

Дальнейшие результаты в разделе 4.7 относятся именно к этим 116 samples. Остальные samples исходного набора либо не прошли ручную валидацию, либо относятся к другим классам, либо имеют статус `Too old`.

#### 4.7.2. Набор данных и признаки

| Параметр | Значение |
|---|---:|
| Валидированных samples (статус «Valid») | 118 |
| После отбора классов «Wildfire» и «Logging» | 116 (74 «Logging» / 42 «Wildfire») |
| Обработано снимков Sentinel-2 | 1 246 (без ошибок чтения) |
| Спектральные признаки | NDVI, NBR, NDMI — среднее, медиана, стандартное отклонение, 10-й и 90-й процентили по пикселям; агрегация по сценам медианой |
| Признаки Scene Classification Layer | доли классов 2, 4, 5, 6, 7 |
| Признаки перехода PRE → POST | абсолютное изменение и относительное изменение по каждой статистике |

Маска валидных пикселей: `dataMask > 0` и класс Scene Classification Layer не входит в набор {0, 1, 3, 8, 9, 10, 11}. Агрегация спектральных статистик между сценами одного периода выполняется медианой, чтобы снизить влияние отдельных облачных сцен.

#### 4.7.3. Схемы кросс-валидации

Использованы две схемы:

- случайное стратифицированное разбиение (5 фолдов) — для сравнения с предыдущими экспериментами;
- разбиение по году события (`GroupKFold` по `hansen_event_year`, 5 фолдов, 10 лет) — для проверки качества на незнакомых временных периодах.

Все пять фолдов второй схемы содержат оба класса и в обучающей, и в проверочной части, поэтому утечки по году события нет.

#### 4.7.4. Основные результаты

| Модель | F1-macro, случайное разбиение | F1-macro, разбиение по году события |
|---|---:|---:|
| Полный набор (19 признаков) | 0.916 | 0.916 |
| Только POST (5 признаков) | 0.907 | 0.907 |
| Только PRE (5 признаков) | 0.839 | 0.851 |
| Только переход PRE → POST (6 признаков) | 0.785 | 0.782 |
| Только Hansen (3 признака) | 0.813 | 0.809 |
| Мажоритарный класс (baseline) | 0.389 | 0.389 |

#### 4.7.5. Отдельные признаки

| Ранг | Признак | F1-macro |
|---:|---|---:|
| 1 | `ndmi_median_post` | 0.926 |
| 2 | `nbr_median_post` | 0.916 |
| 3 | Все признаки PRE (5) | 0.834 |
| 4 | Все пространственные (широта и долгота) | 0.832 |

#### 4.7.6. Feature importance, разложение сигнала и выводы

**Основные наблюдения по признакам:**

- **Пространственное смещение подтверждено напрямую.** Долгота в одиночку различает классы с F1-macro = 0.822, широта и долгота вместе — 0.832. Samples классов «Wildfire» и «Logging» систематически разнесены по территории, поэтому часть качества полной модели объясняется региональной привязкой, а не самим событием.
- **Один признак превосходит полную модель.** Влажность после события (`ndmi_median_post`) в одиночку даёт F1-macro = 0.926 против 0.916 у модели на 19 признаках. При объёме выборки 116 samples полная модель переобучается.
- **Единственный устойчивый сигнал самого события — относительное изменение NBR.** Признак `nbr_median_rel` даёт F1-macro = 0.771, устойчиво при разбиении по году события, и не является пространственной координатой.
- **Разделимость по исходным условиям сильнее, чем по событию.** Признаки PRE в целом дают F1-macro = 0.851, признаки перехода — 0.782.
- **Confusion matrix полной модели (разбиение по году события).** Из 116 samples верно классифицированы 107: 70 «Logging» и 37 «Wildfire». Ошибки — взаимная путаница классов: 4 «Logging» предсказаны как «Wildfire» и 5 «Wildfire» как «Logging».

**Разложение общего сигнала.** Полная модель на 19 признаках даёт F1-macro = 0.916. Вклады по группам признаков:

| Компонент | Оценка F1-macro |
|---|---:|
| Пространственное смещение (широта, долгота) | ≈ 0.83 |
| Исходная влажность (NDMI до события) | ≈ 0.84 |
| Чистый сигнал события (относительное изменение NBR) | ≈ 0.77 |
| Переобучение на 19 признаках | снижает итог |

**Итоговая интерпретация.** Высокое значение F1-macro у полной модели не означает, что модель научилась различать природу нарушения. Большая часть качества объясняется исходными условиями и географией samples, и только около 0.77 F1-macro приходится на сам спектральный отклик события.

**Значение для проекта.** Обычно модель обучают на всех признаках сразу и судят о её качестве по итоговой метрике. В нашем случае такой подход дал бы F1-macro = 0.92 и вывод «модель хорошо различает Wildfire и Logging». Разбор по группам признаков показал, что это не так: большая часть качества достигается за счёт того, что samples двух классов лежат в разных регионах и в разных по влажности лесах. Если подать модели новые samples из тех же регионов, но с другим типом нарушения, она, скорее всего, ошибётся, потому что настоящего сигнала о природе события в ней мало.

Поэтому в дальнейшей работе имеет смысл опираться на две вещи. Первая — проверять вклад признаков до того, как делать выводы о качестве модели: без этого легко принять умение модели определять регион за умение различать типы нарушений. Вторая — при пополнении выборки собирать пары Wildfire/Logging в одних и тех же регионах, чтобы различие между классами определялось событием, а не географией. Сейчас таких пар почти нет, и именно поэтому в признаках сильнее проявляются различия между регионами.

## 5. Что означают текущие рабочие статусы

| Статус | Смысл |
|---|---|
| `Too old` | Событие произошло раньше 2016 года. Для него нельзя корректно собрать Sentinel-2 PRE/EVENT/POST-контекст, поэтому точка исключается из нового Sentinel-поиска. |
| `Valid` | Точка потенциально пригодна для дальнейшего анализа и формирования ML-выборки. |
| `Wrong` | Предполагаемое Hansen/source-событие не соответствует наблюдаемому изменению либо sample непригоден для выбранной постановки. |
| `Unclear` | По Hansen и доступному PRE/POST-контексту нельзя надёжно определить или подтвердить событие. |
| `GOOD` | Hansen-анализ дал достаточно согласованный dominant event year. |
| `AMBIGUOUS` | Hansen показывает потерю леса, но событие не выглядит достаточно однозначным. |
| `NO_LOSS` | В выбранной области Hansen не показывает loss event. |
| `Multiple loss events` | В области sample обнаружено несколько годов потери леса после 2016 года. |
| `Excluded Sentinel scene` | Снимок сохранён в кэше, но помечен как непригодный для использования в выборке. |
| `CLOUDS` | Снимок исключён из-за локальной облачности в AOI: SCL classes `8`, `9`, `10`, `cloud_fraction > 0.10`. |
| `CLOUD_SHADOW` | Снимок исключён из-за cloud shadow: SCL class `3`, `shadow_fraction > 0.35`. |
| `NO_DATA_OR_BLACK_PIXELS` | В AOI слишком много no-data или пустых/чёрных пикселей: `nodata_fraction > 0.10`. |
| `DARK_AND_LOW_CONTRAST` | Clear pixels одновременно слишком тёмные и низкоконтрастные по правилу `p95 < 350` и `range < 100` или `relative contrast < 0.30`. |
